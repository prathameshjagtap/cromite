# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

Cromite is a privacy-focused **Chromium fork** (a fork of Bromite) for Android, Windows, and Linux. This repository is **not a standalone codebase** — it contains no Chromium source. Instead it is a **patch set** that is applied on top of a specific upstream Chromium release. The actual product is built by:

1. Checking out the Chromium tag named in `build/RELEASE` (e.g. `148.0.7778.168`).
2. Applying every patch listed in `build/cromite_patches_list.txt`, in order, via `git am`.
3. Building with the GN args in `build/cromite.gn_args` (merged with platform-specific args).

When asked to "change a feature" or "fix a bug," you are almost always editing or creating a **patch**, not source files. The Chromium tree lives outside this repo (conventionally at `~/chromium/src`); this repo is conventionally cloned at `~/cromite`, and the tooling scripts hardcode those paths.

## Repository layout

- `build/patches/*.patch` — the ~327 patches that define Cromite. Each is a `git format-patch`-style file. Subjects/filenames carry semantic meaning (see conventions below). Patches under `changed/` and `contrib/` subfolders exist in the list but are applied from the same directory.
- `build/cromite_patches_list.txt` — the **ordered** list of patches to apply. Order matters; patches build on each other. Lines have prefixes that the apply tooling interprets (see below).
- `build/cromite.gn_args` / `build/chromium.gn_args` — GN build configuration (privacy/feature toggles, `proprietary_codecs`, etc.).
- `build/RELEASE` — the exact upstream Chromium version/tag the patches target.
- `build/userscripts/` — bundled user scripts (e.g. background video playback).
- `tools/*.sh` — the patch development workflow (see below).
- `tools/under-control/` — snapshots of selected upstream files (`file_list.txt` drives `get_files.sh`) used to detect upstream API changes between rebases.
- `tools/cves/`, `tools/filters/`, `tools/tests/` — CVE tracking, experimental adblock filters, and test harnesses (WebDriver, CreepJS).
- `docs/` — user/developer docs. `PATCHES.md` is **auto-generated** from patch metadata; do not edit it by hand.
- `.github/workflows/` — CI. `build_cromite.yaml` does release builds (self-hosted runner + Docker image `uazo/cromite-build:VERSION-SHA`); `check-git-apply.yaml` verifies patches still apply.

## Patch conventions (critical)

Every patch file follows a strict format enforced by review and tooling:

- **Subject and filename must match.** `Subject: Alternative cache (NIK-based)` → `Alternative-cache-NIK-based.patch` (spaces become hyphens).
- The commit message body should explain *what* and *why*.
- A `License:` line (e.g. `License: GPL-3.0-only - https://spdx.org/licenses/GPL-3.0-only.html`) is expected.
- A `FILE:<filename>.patch` marker in the commit message ties the in-tree commit to its exported patch file; the export tooling strips it from the final file.
- Patches exported from commits whose message contains `NOEXPORT:` are intentionally not written to disk.
- Many features are exposed as runtime **"cromite flags"** (`chrome://flags`-style), introduced by `Add-cromite-flags-support.patch`. New user-facing toggles typically follow that pattern rather than hardcoding behavior.

### `cromite_patches_list.txt` line prefixes

The apply tooling (`tools/apply-all-patch.sh`) treats the first character of each line specially:
- plain filename → apply the patch from `build/patches/`
- `#cmd` → execute `cmd` as a shell command (not a patch)
- `-name` → skip this patch
- `=name` → (re)create the patch from working tree changes via `create-from-patch.sh`
- `1name` → apply from the `patches-new/` regenerated directory

## Development workflow

There is no `make`/`npm build` here — building means driving Chromium with these patches, normally inside the prebuilt Docker image (`uazo/cromite-build:$VERSION-$SHA`, see `docs/HOW_TO_BUILD.md`). The scripts in `tools/` are the real "commands" of this repo and assume `~/cromite` and `~/chromium/src` exist:

- **Apply the full patch set** onto the Chromium tree (with auto-wiggle of rejects):
  `bash tools/apply-all-patch.sh`
  Set `SILENT=1` for non-interactive runs, `SKIPAUTOGENERATED=1` to skip domain-substitution patches.
- **Apply one patch** and re-export it: `bash tools/apply-single-patch.sh <path-to.patch> <new-dir>`
- **Create/refresh a patch** from staged working-tree changes: `bash tools/create-from-patch.sh <path-to.patch>`
- **Export all patches** from the Chromium commits back into `build/patches-new/`: `bash tools/export-all-patch.sh` (single commit: `tools/export-single-patch.sh <sha> [filename]`).
- **Regenerate `docs/PATCHES.md`**: `bash tools/extract-all-patch-data.sh build/patches`
- **Refresh upstream file snapshots**: set `CHR_SOURCE_DIR`, `OUTPUT_DIR`, `FILE_LIST`, then `bash tools/under-control/get_files.sh`.

Editing flow in practice: apply patches to the Chromium tree → make the change as a commit (with `FILE:` marker) in that tree → export it back into `build/patches/` → update `build/cromite_patches_list.txt` if adding/removing a patch.

### Rebasing to a new Chromium version

Bumping `build/RELEASE` means re-applying all patches against the new tag. `apply-single-patch.sh` auto-resolves conflicts with `wiggle` where possible and stops for manual fixing otherwise (writing `cromite_patches_list_ok.txt` / `cromite_patches_list_failed.txt`). The `tools/under-control/` snapshots help spot upstream API/IDL changes that break patches.

## Conventions

- `.editorconfig`: 2-space indent, **CRLF** line endings for `*.yaml`, `*.sh`, `*.gn_args`.
- Patch files are normalized with `dos2unix` during apply; keep them in the exported format the tooling produces (zero-commit, full-index, no signature).
- When adding a feature, mirror the existing pattern: gate it behind a cromite flag, add the patch with a matching Subject/filename and License line, and insert it at the right position in `cromite_patches_list.txt`.
